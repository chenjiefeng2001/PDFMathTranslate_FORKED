主判据是**产物而非日志**：render_plan 的块字号众数 vs 源 PDF 页众数字号，两轮用同一把
尺子。

残余 7.3% 主要来自**指标本身**：比的是「块字号众数」对「页字号众数」，而标题/图注块

## 3. 内容丢失：2 处，且都有日志（无静默丢失）

这是「不溢出、不静默裁字」这条硬要求的直接检验。判据用**渲染后 PDF 的文本**，
不是 `render_payload` 的内部结构（同一份计划里就有三种形态：flow 的
`commands`、toc 的 `toc_commands`、shift_down 干脆没有 payload）。

```
log 'line(s) dropped' warnings: 2
  needs 2, 1 fit in 15.0pt -> dropped 1 (50%)   '1.2 一个寓言'
  needs 6, 1 fit in 16.0pt -> dropped 5 (83%)   '关于N，所使用的核心数量。依赖关系是\begin{array}...'
REAL content loss                                    : 2
```

告警数 2 与 PDF 实测丢字数 2 **完全吻合**，交叉验证通过。

### 根因 1：缩放阶梯**结构上**救不了这类块

`_WRAP_SHRINK_STEPS = (1.0, 0.92, 0.85, 0.78, 0.72, 0.66, 0.60, 0.55)`，下限 0.55。
`doc/7p5_wrap_repro.py` 实测 `p25_1`（`1.2 一个寓言`，框 67.0×15.0pt，字号 16.65pt）：

```
whole-string width at 16.65pt : 133.2pt  (box 67.0pt)  -> WRAPS
 scale  fontsize  lines  stack_h  fits?
   0.92     15.32      2     34.47    no
   0.85     14.15      2     31.84    no
   0.78     12.99      2     29.22    no
   0.72     11.99      2     26.97    no
   0.66     10.99      2     24.73    no
   0.60      9.99      2     22.48    no
   0.55      9.16      2     20.60    no   <-- 缩到下限仍需 2 行
 -> NO scale in the ladder fits -> lines get dropped
```

（我最初手算以为 0.55 时能缩成 1 行，实测否掉了：9.16pt 时整串宽 73.3pt > 框宽 67pt。）

**这类块需要的不是把字缩到看不清，而是把框撑开** —— 标题下方通常有空白。

### 根因 2：一个 LaTeX 公式被并进了标题块

`p36_8` 的 `translated` 有 86 字符，其中含
`\begin{array}{r}{CacheMiss=\frac{N^{\bullet}}{N+10}}\end{array}`。公式本该是独立块，
塞进标题后，16pt 高的框要装 6 行 —— 缩放当然救不了。

## 5. 顺带修掉的工具缺陷

`doc/7p2_watch.py` 的阶段标签曾返回 `degraded_to_legacy`，触发条件只是日志里出现并页警告，
而那次并页**实际上重解析成功了**（`page 6 re-parsed cleanly; quarantine lifted`）。更糟的是
它排在判断链前面，把后续 translate/render 阶段整个遮住 —— 整轮 50 页真跑全程只显示这一个
标签，差点被误判成整轮跑废。

- 改为 `merged_pages_detected` / `reparse_recovered`
- 判断顺序改为**阶段时序倒序**（累积日志里旧标记永不消失，先命中先返回必然遮蔽后续）

修后实测阶段推进：`starting → parse → merged_pages_detected → reparse_recovered → render`。

## 6. 下一步修复方案（建议）

### P1 — 停止丢行：装不下就扩框，显式溢出，不再静默丢字 ✅ 已完成

改 `pdf2zh/v3/magicpdf_renderer.py::_insert_text_wrapped`：阶梯走完仍装不下时，
按顺序

1. 计算所需高度；若页内下方有空白且无碰撞 → **向下扩框**并画全部行；
2. 否则标记显式 `overflow`（`policy=preserve`）并**照样画全部行**，计入指标；
3. 仅在退化几何（零高 box）下保留"只画首行"的历史行为 —— 既有测试锁定了它。

这是唯一违反硬要求的地方，优先级最高。

**实际实现**（`783fe37` 之后，`HEAD` 见下）比原方案多两级，因为实测证明单靠扩框不够：

| 级 | 触发条件 | 行为 | 指标 |
|---|---|---|---|
| 1 常规阶梯 | 一直有 | 缩到 0.55 | `fit_shrunk` |
| 2 **深缩** | 1 装不下 | 缩到 0.35~0.50，但**绝对不低于 5.0pt** | `fit_shrunk_deep` |
| 2' **最小步兜底** | 2 的每一档都装不下 | 取最小档（不退回原始字号） | `fit_shrunk_best_effort` |
| 3 **扩框** | 仍装不下 | 向下扩，页底有余量且不与邻居相撞 | `box_expanded` |
| 4 显式溢出 | 扩框被挡 | 页内画满全部行 | `wrap_overflow_preserved` |
| 5 显式截断 | 页面也放不下 | 计入并告警 `CLIPPING (not silent)` | `wrap_clipped_page` |

**为什么必须有第 2 级**：实测 mp2e page 25 的 `1.2 一个寓言`（框 67.0×15.0pt，字号
16.65pt），常规阶梯最低 0.55 时整串宽仍 73.3pt > 框宽 67pt —— **每一档都还是 2 行**。
我最初手算以为 0.55 能缩成 1 行，实测否掉了。深缩到 0.35 时字宽 46.6pt < 67pt，变回 1 行。

**为什么"深缩"排在"扩框"之前**：深缩把文字**留在原框内**，不与任何东西相撞，因此不会
加重已经存在的叠印（叠印本来就是待归因项，见 §4）。

**为什么第 2' 级不能退回原始字号**：40pt 塞进 12pt 框时，若"没有一档装得下"就退回 40pt，
一页只画得下开头几行、后面整段全丢。取最小候选至少能保住大半。

#### P1 过程中修掉的三个真实缺陷

1. **坐标空间不一致**：避让名单用 `dst_box`（PDF 左下原点），而扩框判断发生在 fitz
   坐标里 —— 碰撞检查在真实渲染中**永远判为不相撞**，静默失效。现已统一翻到 fitz。
   单测用未翻转的框算出 `overlap=True`，接进真实渲染却照样扩框，就是它暴露的。
2. **首行无条件落笔**对真实框也生效：框本身就在页底之下时，首行直接画到页外。已改为
   只对退化几何保留。
3. **页底夹取重复计算**：曾额外减 0.25em 下伸部余量，跨 7 种字号 × 11 个位置共 77 组
   几何扫描证明它一例越界都多挡不下（最低字形底 791.6 < 页高 792），却白白多跳过 7 组
   本来画得下的几何。已删除，2.0pt 余量本身足够。

### P2 — 别让公式混进标题文本 ✅ 已完成

在 `annotate_roles` 里加一道守卫：**LaTeX 主导的块判为 `formula`，不参与标题判定。**

#### 定位（`doc/7p2_locate_formula.py` 可在真实 mp2e 上复现）

一开始怀疑是 MinerU 把公式内联进了文本。**实测不是**：

- 扫 50 页 MinerU 的 block 级 `text`：含 LaTeX 的文本块 **0 个**；
- 但那页的 block 级 `text` 与 `span.content` **不一致** —— LaTeX 在 **span 的 content** 里。
  只扫 block text 会完全漏掉这一层（我第一次就是这么查的，得出"语料里没有公式"的错误结论）。

真实因果链：

1. MinerU 把行间公式塞进某个 **span 的 `content`**；
2. 该 span 框高 **16.0pt**，明显高于同页正文的 9~11pt；
3. 字号校准把它如实映射成 15.95pt —— **这一步是对的**，公式本来就比正文高；
4. `apply_layout_splits` 把这一行单独拆成块；
5. `StructureClassifier` 见字号远大于正文 → 判成 **`heading`**。

于是公式冒充标题被送去翻译，再被当成标题塞回 16pt 的框里。**根因在第 5 步，不在渲染。**

#### 判据被真实样本逼着换过两次

三个直觉指标**每一个都会误判**，两次都写进了代码注释：

| 指标 | 为什么不行 |
|---|---|
| 有无反斜杠 | 正文行内上标 `M ^ { \prime }` 也有 → 整段正文被判成公式、**完全不翻译** |
| 首末标记之间的跨度 | 某正文块有**两处** `\prime`（一前一后），区域横跨整段 174 字符散文 → 占比 0.78 → 整段正文被判成公式 |
| 字符密度 | `M ^ { \prime }` 只有 7 个非空白字符，纯密度必然高（0.29）→ 误判 |

最终用**两个条件同时成立**：

1. **结构**：公式区里有带花括号参数的命令（`\frac{..}{..}` / `\begin{..}` / `\sqrt{..}` …）。
   这是把 `\frac{a}{b}`（公式）与 `^ { \prime }`（上标）分开的关键 —— 后者的命令**没有参数**。
2. **密度**：公式区里 `{ } \ ^ _ = + - * / 0-9` 占非空白字符 ≥ 0.25。

另外结构白名单是**显式枚举**，不是 `\\[a-zA-Z]+`：后者会把 `\n`、`\t`、`\r` 也当成
LaTeX 命令，于是"公式区域"从一个 `\n` 一路跨到块尾，整段正文被吞掉（实测某块 174 个
非空白字符里有 6 个在 `\prime`、其余 129 个在 `\n` 之后，尾段占比算成 0.78）。
