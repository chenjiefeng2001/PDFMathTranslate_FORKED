# 7P2 — 对照实验:修复前 vs 修复后(同语料 / 同模型 / 同 50 页)

两次都是**真跑**生产 CLI:

| | BEFORE | AFTER |
|---|---|---|
| 产物 | `doc/7p0-load50`(7P0 那轮) | 本轮 `fix50` |
| HEAD | 7P0 时点 | `2e7c7f4` |
| 引擎 | magicpdf(MinerU) | **legacy(降级)** |
| 墙钟 | 5341s(89 min) | 2931s(49 min) |
| 模型 | `nvidia/nemotron-3-ultra-550b-a55b:free` | 同 |
| 页范围 | 1-50 | 同 |

---

## 0. 先说最重要的一条:两次**不是同一个渲染器**

P0 的合并页检测在第 7 页拦下了目录折叠:

```
[magicpdf] ERROR 版面模型把多个源页并进了同一 render 页
           (page 6: 327 lines, 2.03pt/line, implies 5.83 page(s));
           继续渲染会产出整页叠影，按解析不可用降级
[magicpdf] WARNING ... 按解析不可用降级（请改用 --parse-engine legacy 等）
```

于是**整篇 50 页退到了 legacy 内核**。这是 P0 那个降级决策的真实代价,也是这次
对照最该被看见的事实:

> 这个对照**不能**回答"magicpdf 修好之后质量提升多少"。它回答的是另一个问题 ——
> 折叠被拦住之后,降级交付 与 直接交付一页叠影 相比,是什么关系。

`doc/7p2_compare_runs.py` 每次运行都会先打印这条警告,就是为了不让这份表被误读。

## 1. 对照表(前 50 页)

| 指标 | BEFORE (magicpdf) | AFTER (legacy 降级) | |
|---|---|---|---|
| 墙钟 | 5341s | 2931s | **−45%** |
| render-plan 块数 | 621 | — | legacy 不产 render_plan |
| 单页最多块数 | **201** | — | 目录折叠页 |
| 译文覆盖率 | 0.942 | — | 无 render_plan |
| 原文非空却空译文 | 0 | 0 | |
| **叠印页(渲染器口径)** | **11** | **16** | **+45%** |
| 叠印页(不忽略背景) | 41 | 18 | −56% |
| 越界 span | **0** | **3** | +3 |
| 含中文的页 | 42 | **47** | +12% |

### 怎么读这张表

**变好的:**
- 目录折叠页不再出现(那一页 201 个块叠在一起,是 BEFORE 里最严重的缺陷)。
- **墙钟 −45%**:并发修复生效(实测 3.12×,见 `doc/7p1-concurrency/bench.json`),
  叠上降级路径本身更快。
- **含中文页 42 → 47**:legacy 路径把 50 页里更多页真正译出来了。

**变差的(必须如实说):**
- **叠印 11 → 16 页**。legacy 内核的几何比 magicpdf 差。
- **越界 0 → 3**。magicpdf 路径此前是 0,BEFORE 的渲染器更干净。
- 也就是说:**P0 用"整篇降级"换掉了"一页叠影",代价是几何质量下降。**

这个取舍是否划算,取决于你怎么看:叠印是**肉眼可见的废品**(第 7 页 201 个块互相
覆盖、目录条目查不到),越界 3 个 span 只是轻微溢出。但它同时意味着**magicpdf 的
排版优势在这本书上被完全放弃了** —— 而那个优势是 6e06c3a 以来所有工作的目的。

## 2. 测量方法上的三次自我纠正(全部是同一个错误)

写对照脚本时我三次把"没测到"或"测法不同"报成了数字,都记在这里:

1. **叠印 41 vs 11** —— 我另写了一套独立复算,没排除背景 span,把"原文 + 覆盖其上
   的译文"全算成叠印。渲染器的 `_span_key` 注释里就写着这个坑,我读漏了。
2. **`-mono.pdf` vs `_mono.pdf`** —— magicpdf 命名 `*_mono.pdf`,legacy 命名
   `*-mono.pdf`。只匹配一种 → 降级那次"找不到产物",几何整排 None,一度以为产物丢了。
3. **忽略集用近似而非复现** —— 我直接读源 PDF 的 span 当背景集,而渲染器是
   `show_pdf_page` 之后再快照,坐标取整不同 → 键对不上、一个背景 span 都排除不掉 →
   BEFORE 又变回 41。**与第 1 条是同一个坑,踩了两次。**

最终 `audit_page_geometry` 是**直接调用渲染器自己的函数**、忽略集**如实复现**
(`show_pdf_page` + `page_span_snapshot`),不再另写一套。

还有一个测量陷阱:legacy 会把译好的 50 页**嫁接回 562 页原书**,所以产物是全书页数,
只有前 50 页含译文。不限定页范围就会把 512 页未翻译原文算进指标(实测
`pages_with_cjk=47`,而总页数 562)。

## 3. 心跳监听为什么改成独立进程

按要求改用脚本 + 心跳,途中暴露两个真问题:

1. **watcher 放在 launcher 里 = 没有心跳。** launcher 发完就该退,线程随之消失。
   实测:运行早已完成(`run-summary.json` 存在、退出码 0、耗时 2931s),而
   `heartbeat.json` 从未出现,**看起来像挂了 47 分钟**。现在 watcher 是独立的
   只读附加进程(`doc/7p2_watch.py`),给它 pid 和日志路径即可。
2. **`os.kill(pid, 0)` 在 Windows 上抛 `SystemError` (WinError 87)** —— 它把 0 当成
   真实信号量了。改用 `tasklist` 查。

另外 `opencode serve --port N` 会 spawn 真正的 `opencode.exe`,pwsh 只是包装层。记
包装 pid 会让 `serve-stop` 杀不掉真身(包装活着、端口无人监听),下一轮就撞上端口占用。
现在按端口用 `netstat -ano` 反查真实 pid。

## 4. 这轮对照**没有**回答的问题

- **magicpdf 修复后的质量收益仍未测。** 要测它,得让 P0 的检测**不触发降级**——
  例如只在目录页重解析、或降级为"该页回退原文"而非整篇换内核。这本身是个待决的
  设计问题(见下)。
- **P0 的降级策略是否该改。** 现在是"一页折叠 → 整篇换内核",粒度太粗。
  更合理的方向是**只重解析那几页**或**只让那几页保留原文**。这是个真缺陷,
  不是配置问题。
- **字号偏小**(`doc/7p2_font_chain_audit.md`)与本对照无关,仍未决。

## 5. 复现

```bash
python doc/7p2_verify_run.py serve-start
python doc/7p2_verify_run.py launch --out <dir> --pages 1-50 --thread 4
python doc/7p2_watch.py --out <dir>            # 独立心跳,可反复执行
python doc/7p2_compare_runs.py --after <dir>
python doc/7p2_verify_run.py serve-stop
```
