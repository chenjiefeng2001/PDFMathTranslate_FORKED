# 7P2 — 字号链路对账:译文比原文小 23% 的成因

调查对象:7P0 真实运行(mp2e 前 50 页)的产物。结论先行:

> 译文渲染成 **7.65pt**、源正文字形是 **9.96pt**,比值 0.77。这不是 SHRINK 触底,
> 而是**我们的 adapter 用「span 行框高 × 0.85」估字号**,而 MinerU 根本不报字号。

7P0 报告里我写的「168 块触字号下限」和「叠印自报口径偏窄」两条 **都不成立**,本文件
一并纠正。

---

## 1. 逐环对账(0-based page 14 / PDF 第 15 页)

| 环 | 来源 | 该页字号 |
|---|---|---|
| 0 | 源 PDF 真实字形(`get_text` span size) | **9.96pt**(73/74 spans) |
| 1 | MinerU 原始输出 | span `size = 0`(不报);行框高 **9.0pt**(20 行) |
| 2 | 我们的 `document.json` | `line_sizes` / `font_size` = **7.65pt** |
| 3 | `render_plan` | **7.65pt**(与 ring 2 相同) |
| 4 | 成品 PDF | 译文 7.65pt vs 同页原文 11.29pt = **68%** |

另两页(15、21)结论一致。

### 关键否证:没有 SHRINK 在发生

```
ring 3  payload.overflow  : {'False': 7, 'None': 1}
ring 3  payload.recovery  : {}          <- 空
ring 3  render_path       : {'translate_refit': 7}   <- 全部 keep
```

若 SHRINK 阶梯真的在跑,`recovery` 里会有 `{"decision": "shrink", ...}` 且
`overflow` 会转 True。两者都是空/False —— **字号从 ring 2 起就没再被动过**。

所以「触底」「触下限」这类说法没有事实基础,是我把「7.65 这个值反复出现」误读成了
「被钳位」。实际它是 `9.0 × 0.85` 的构造值,所以 7.65 / 9.35 / 8.50 / 10.20 全是
`行高 × 0.85` 的整数倍。

---

## 2. 根因定位

`pdf2zh/v3/magicpdf_bridge.py`(`MagicPdfBridge.convert`,参数 `n: float = 0.85`):

```python
size = max(0.0, float(sbox_tl[3]) - float(sbox_tl[1]))   # MinerU 的 span 行框高
sm = SpanModel(size=round(size * self.n, 2) if size else 0.0, ...)
```

然后 `pdf2zh/v3/canonical_page.py::annotate_style` 把这个 span 尺寸当作字号传播:

```
SpanModel.size → _block_font_usage → metadata["font_size"] / ["line_sizes"]
              → _node_font_size → render_plan.font_size → 落笔
```

链路里**没有任何一处**去读源 PDF 的真实字形尺寸。原因也说得通:MinerU 的 span
`size` 全是 0(见上表 ring 1),而 magicpdf/MinerU 的输出结构里没有可用的字号字段,
所以 adapter 只能拿几何高度去估。

**估得偏小 23%**:真实字形 9.96pt,行框只有 9.0pt(MinerU 的行框比字形紧,即行距压缩),
再乘 0.85 就到了 7.65pt。

---

## 3. 这不是 bug,是取舍 —— 需要你决定

`n = 0.85` 是**刻意保守**的:行框 9.0pt 而字形 9.96pt,若按真实字号落笔,字形会略微
溢出行框,进而触发换行/裁剪。也就是说:

| 方案 | 收益 | 代价 |
|---|---|---|
| A. 保持 0.85 | 不会溢出行框;稳定 | 译文明显小于原文(当前) |
| B. 校准到 ≈1.1(贴合源字号) | 视觉一致 | 可能触发溢出/裁剪,需重跑验证 |
| C. 从源 PDF 实测每 span 字形尺寸 | 最准 | 实现复杂、需 span↔源对齐,有回归风险 |

我不擅自选,因为:

1. 这三个方案对 4783 个测试基线的影响面完全不同;
2. B/C 的收益(视觉一致)必须用**重新渲染一整本书**来验证,不是几秒钟能确认的;
3. 而 A 的现状并不会产生任何告警 —— 它只是"不好看",不是"坏"。

---

## 4. 与 7P0 其他修复的关系

字号偏小**不会**掩盖前几项已修的缺陷:7.65pt 的译文仍能容纳在 9.0pt 行框里,换行
(P1 已修)、目录折叠(P0 已修)都不依赖字号。所以这是一个**独立的观感问题**,不阻塞
已完成的修复。

## 5. 同批纠正:叠印自报口径(7P0 §6 的结论作废)

我曾说「渲染器报 11 页、实测 41 页,口径偏窄」。用 `audit_page_geometry` 对同一产物复算:

| 口径 | 叠印页数 |
|---|---|
| 不忽略任何 span | 41 |
| **忽略背景 span(渲染器实际使用)** | **11** |

忽略集排除 **8863 个背景 span、只留 988 个本次绘制的**。我的独立复算
(`doc/7p0_real_load_analyze.py`)没有排除背景,把「原文 + 覆盖其上的译文」全算成了叠印。

渲染器的 `_span_key` 注释里本就写明了这个坑:

> 不做区分的话,每个翻译块都会与它覆盖掉的原文报一次重叠,审计立刻变成噪声。

是我读漏了已有实现、另写了一套。残留的 11 页叠印是 7P0 目录折叠的下游症状,已随 P0 修复。

## 6. 后续:方案 C 已落地,并推翻了本文件 §2/§3 的部分推断(2026-10)

§2/§3 是**基于未测量的推断**,实测后有两处必须纠正。

### 6.1 纠正一:0.85 不是"保守",是猜错了

§2 说「MinerU 的行框比字形紧(行距压缩),行框 9.0 而字形 9.96」,据此推出方案 B
「校准到 ≈1.1」。**这个 1.107 是拿页级众数算出来的,而众数本身不可靠**:

| 事实 | 测量 |
|---|---|
| 源 PDF 里「字号 ≈ 行框高」 | 比值 **1.00**,264 行,**每档纯度约 100%** |
| MinerU span 框高 ≈ 源的**行框**高 | delta **≈ 0.0**(不是差 1.0pt) |
| MinerU 对同一段 9.96pt 正文 | 框高时而 **9.0**、时而 **10.0** |

最后一行是全部关键:MinerU 的框高有 **±0.5pt 量化抖动**。任何单一系数都无法同时把
9.0 和 10.0 映射到 9.96。

**实测:页级比例方案在真实页面上把平均误差从 9.9% 恶化到 15.3%**(8 页里 5 页更糟) ——
比例继承了众数的抖动,再套到该页**所有**块上,连标题/图注(框 11.0)也被正文比例放大。
这条负结果直接否掉了方案 B。

### 6.2 纠正二:不需要 span↔源对齐

§3 说方案 C「实现复杂、需 span↔源对齐」。实测**不需要**对齐:因为源里「字号 = 行框高」
成立,MinerU 的框高又与源行框高相等,所以只要从源 PDF 收一张
`{行框高 → 字号}` 的表,再按**最近邻**匹配 MinerU 的框高就行:

```
MinerU 9.0  -> 最近源框 10.0 -> 9.96pt
MinerU 10.0 -> 最近源框 10.0 -> 9.96pt      (抖动落在容差内)
MinerU 15.0 -> 最近源框 13.4 -> 13.45pt     (次级标题保住自己的档)
```

### 6.3 最终实现

- `pdf2zh/v3/magicpdf_bridge.py`:新增 `SizeCalibration` / `calibrate_size_map()`,
  按页查表 + 最近邻(`SIZE_LOOKUP_TOL = 2.0`pt)。查表未命中才退回按出现次数加权的
  比例,再兜底 `DEFAULT_SIZE_SCALE = 0.85`。
- `pdf2zh/magicpdf_adapter.py`:新增 `_annotate_size_scale()`,收 **span** 框高(不是行框
  高),挂在 `raw["size_map"]`;`parse()` 的切片与整篇两个分支都接线。
- 源 PDF 读不到 / 加密 / 截断 / 无文本层 → 不挂表,退回 0.85,**绝不阻断解析**。

### 6.4 实测结果(mp2e,12 页;探针 `doc/7p2_font_calibration_probe.py`)

| 指标 | 校准前 | 校准后 |
|---|---|---|
| 块字号众数相对源页众数的平均误差 | **11.5%** | **3.5%** |
| 精确命中源字号(9.96pt)的页数 | 0 / 12 | **7 / 12** |
| 字号 > 行框高 × 1.4 的违规 | 0 | **0** |

逐页表里标 `WORSE` 的几页是**指标假象**:那些页的众数**块**是图注(10.96pt),而 10.96pt
正是该页图注的真实字号 —— 块众数与页众数不是同一个量。

### 6.5 「不溢出」是怎么保证的

查表给出的是**源 PDF 自己的字号**,而源文档就是用这个字号排进那个框的,所以它不可能比
原文更容易溢出;真正放不下的块仍由 `pdf2zh/semantic/layout/adaptive.py` 的
WRAP → SHRINK → CLIP 阶梯缩回去。测试用「30×14pt 框塞长句」直接驱动布局层,断言字号
被缩过且 `overflow` 如实上报。
